# Fixture provenance

Synthetic example. Not SORT4CIRC project data.

Thirteen of the fourteen JSON files here are generated by `SyntheticFixtureFactory`
([`../../src/sort4circ_dpp/synthetic.py`](../../src/sort4circ_dpp/synthetic.py)). Dates,
identifiers, organisations and claims are fictional, drawn from the reserved
`urn:example:` and `https://example.org/` namespaces.

`valid-annex-g-garment.json` is the exception. It reproduces the worked example published
as Annex G of the source specification, so it is maintained by hand rather than
generated: a change to the generator must not be able to move a published record. Its
values — including the `TXHO-WP3-B01-001` sample label, the `urn:sort4circ:` identifiers
and the SGTIN — are themselves synthetic and were authored as illustration. It is kept
byte-stable so that this repository, the published specification and the canonical digest
vector in [`tests/test_canonical.py`](../../tests/test_canonical.py) all describe the same
item.

It declares `"schemaVersion": "1.0.0"`, the profile version it was published under.

Provenance: the record originates in project deliverable D4.3, *DPP Development
Guidelines*, Annex G.

Nothing here describes any organisation's commercial activity, material intake, processes,
performance or capabilities.

The `valid-*` files must validate. The `invalid-*` files must fail, each violating exactly
one profile rule, and each carries a test-only `$expect` member naming the reason code it
must produce. A negative fixture that stops failing is a silent gap in the schema, which is
why the expected code is asserted rather than merely the absence of success.

`$expect` is not a schema member. The fixture runner removes it before validating; the CLI
does not.

~~~sh
python tools/validate_fixtures.py
~~~

See [Validation](../../docs/validation.md) for a table of what each fixture proves, and
[Examples](../README.md) for the wider walkthrough.
